## 3. DragonBones POC 结论（✅ 通过 —— 本轮最重要发现）

### 3.1 发现

先前担心「3.x 移除了龙骨、需装外部插件、插件与 3.8.8 兼容性未知」。**实测证伪**：

```
/Applications/Cocos/Creator/3.8.8/.../resources/3d/engine/cocos/dragon-bones/
├── ArmatureDisplay.ts        ← 主组件
├── CCArmatureDisplay.ts
├── DragonBonesAsset.ts       ← 骨骼资源类型
├── DragonBonesAtlasAsset.ts  ← 图集资源类型
├── ArmatureCache.ts / ArmatureSystem.ts / CCFactory.ts / CCSlot.ts / AttachUtil.ts / CCTextureData.ts
├── assembler/{index,simple}.ts
└── index.ts / index.jsb.ts
exports/dragon-bones.ts → export { dragonBones }
```

且工程模块裁剪开关 `dragon-bones: True`（默认启用，见 `settings/v2/packages/engine.json`）。

> ⚠️ 更正先前判断：我之前用 `grep cc.d.ts` 得 0 命中就断言「3.x 无龙骨」——**错误**。cc.d.ts 是按裁剪配置生成的声明，未含该模块；真相是引擎源码完整内置。教训：判断引擎能力要看 `engine/cocos/` 源码目录，不能只看 .d.ts。

### 3.2 API 对照（2.x 实际用法 → 3.8.8 源码，逐项已核）

| 项目 2.x 用法（实测出现次数） | 3.8.8 源码位置 | 迁移动作 |
|---|---|---|
| `dragonBones.ArmatureDisplay`（49 次） | `ArmatureDisplay.ts:186 export class ArmatureDisplay extends UIRenderer` | 改 import 为 `import { dragonBones } from 'cc'` |
| `.playAnimation("移动-右下", 0)`（22 次） | `:1269 playAnimation(animName: string, playTimes?: number): AnimationState \| null` | **零改动**（签名一致） |
| `dragonBones.EventObject.COMPLETE`（8 次） | `:883 this._eventTarget.emit(EventObject.COMPLETE)` | 命名空间改 `dragonBones.EventObject` 仍可用 |
| `dragonBones.AnimationState`（2 次） | `:26 import { AnimationState } from '@cocos/dragonbones-js'` | 改 import |
| `.armatureName = ...`（3 次） | `:239 get/set armatureName` | **零改动** |
| `@property(dragonBones.ArmatureDisplay)`（2 次） | 同名组件类 | **零改动** |
| `getAnimationNames / getArmatureNames / buildArmature / armature()` | `:1347 / :1332 / :1457 / :1469` | **零改动** |

**结论：龙骨迁移只是 import 路径与命名空间调整，业务调用零改动，2 个涉及文件即可完成。**

## 4. 2.x → 3.x 代码迁移清单（312 处，全部可脚本化）

| 2.x 写法 | 实测处数 | 3.x 对应写法 | 自动化 |
|---|---|---|---|
| `node.opacity = n` | 38 | `node.getComponent(UIOpacity).opacity = n`（需先加 UIOpacity） | ✅ 脚本+人工复核 |
| `zIndex` | 25 | `node.setSiblingIndex(n)`（3.x 移除 zIndex，改兄弟序） | ✅ 需重排序逻辑 |
| `runAction` | 10 | `tween(node).to(...)` | ✅ |
| `cc.moveTo/fadeTo/sequence`（Action 系统） | 12 | `tween` 链式 | ✅ |
| `cc.audioEngine` | 11 | `AudioSource` 组件 + `playOneShot` | ⚠️ 需重构音频管理（建议统一 AudioManager） |
| `cc.loader` | 8 | `resources.load` / `assetManager` | ✅ |
| `node.x = / node.y =` | 13 | `node.setPosition(x, y)` | ✅ |
| `scaleX/scaleY`、`rotation`、`getContentSize/setContentSize`、`convertToNodeSpace/convertToWorldSpace`、`getComponentInChildren`、`cc.find`、`schedule`、`cc.Class`、`_super` 等 | 195 行 | `setScale/setAngle/getComponent(UITransform).contentSize/UI 坐标转换 API/getComponentInChildren(仍可用)/find/schedule(仍可用)` | ✅ 多数机械替换 |
| `dragonBones.*` | 51（2 文件） | 见 §3 | ✅ |
| `import ... from 'cc'` 具名导入 | 全量 | 2.x 是全局 `cc.`，3.x 需 `import { Node, Sprite, ... } from 'cc'` | ✅ 脚本批量加 import |
| 装饰器 `@ccclass/@property` | 275+ | 3.x 需 `const { ccclass, property } = _decorator;` | ✅ 脚本批量注入 |

**迁移策略**：写一个 codemod 脚本做机械替换（80% 工作量）→ tsc 全量校验（报错清单驱动）→ 逐文件人工复核语义差异（opacity/zIndex/音频这三类有语义陷阱）。

## 5. 场景/预制体重建方案

2.x 的 `.fire/.prefab` 与 3.x 的 `.scene/.prefab` **格式不兼容，官方无自动转换器**（3.x 内置的「升级助手」只支持 2.4.x→3.0 的部分自动迁移，且对 452 节点的复杂经营场景不可靠）。两条路线：

| 路线 | 做法 | 优劣 |
|---|---|---|
| **A. 官方升级助手 + 人工修**（先试） | 用 Cocos 的 2→3 升级工具转一次，再人工修不兼容处 | 省节点重建；但工具对自定义组件/龙骨/Widget 的支持需实测，**可能产生大量脏数据** |
| **B. MCP 脚本化重建**（兜底，已验证可行） | 解析 2.x `.fire/.prefab` JSON → 提取节点树/组件/属性/绑定 → 用 MCP `node_create_tree`+`component_manage`+`component_auto_bind` 在 3.8.8 重建 | 全自动化、可 diff、可回归；堆塔项目已验证 MCP 建 600 节点级树可行；**需先写 2.x 场景解析器** |

**建议**：先用路线 A 试转（1 次成本），评估产出质量；不合格则切路线 B。两路线都以「逐屏截图 vs 2.x 运行画面基准对比」验收（2.x 基准图已有：`screenshots/` 与本次预览截图）。

## 9. 风险登记表

| 风险 | 等级 | 应对 |
|---|---|---|
| 场景重建后布局错位（452 节点+Widget 对齐规则 2.x/3.x 有差异） | **高** | 逐屏截图对比基准；Widget 的 alignMode/边距逐项核；MCP 可批量改属性回归 |

| `opacity` 迁移遗漏（3.x 需 UIOpacity 组件，漏加则透明度失效） | 中 | codemod 自动补 UIOpacity + tsc 类型检查兜底 |
| 音频重构（audioEngine → AudioSource）改变播放时序 | 中 | 统一封装 AudioManager，逐个音效对照触发时机 |
| 2.x 升级助手产出脏数据 | 中 | 不合格即弃用，切 MCP 重建（路线 B 不依赖它） |
| 龙骨动画在 3.x 的缓存模式差异（REALTIME/SHARED_CACHE） | 低 | POC 已证 API 兼容；播放异常时切 REALTIME 模式 |
